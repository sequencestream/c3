## 基本要求

- 文档第一读者是人类, 第二读者才是 Agent，优先使用分层和结构化的表述
- 文档要简洁明了
- 保持文档和代码的同步更新:行为变更时,同步的是上层契约(意图、边界、不变量、协作方式、关键取舍),不是实现。代码只改内部拆分、调用、字段铺排或局部控制流,而上述契约不变,文档不动。对照验证的是两边是否描述同一份行为,不是把代码逐条抄进文档

## 宪法级要求 (不可违背)

- **文档停在上层, 细节在代码**: `doc/` 只写比代码高一层的内容——意图、边界、不变量、模块如何协作、关键取舍。不写细节代码设计。细节设计由代码自己实现并自洽;要探索细节,去读代码,不从文档里翻。可以提到模块名、抽象概念或抽象接口的名字;禁止出现代码文件名与源码路径。
  - **过细判定**: 若一次不改变跨模块行为的重命名、抽取或局部重构就能让一句话过时,这句话就不该在 `doc/` 里。禁止写入:函数签名、字段逐项铺排、逐步调用链、分支走法、SDK 参数清单、组件树、错误码对照表。这些以代码为准。
  - **同步不是抄写**: 「与代码同步」只更新上层契约是否仍成立。不得借同步之机把实现细节补进文档,也不得为了「写全」把规格写成实现说明书。
- **双源自洽, 互不引用**: `doc/` 保持自洽,不引用对应代码(不链到源文件)。代码保持自洽,不引用 `doc/` 下的文档;注释同样禁止(含规则编号如 `SR-R14`、ADR 编号、文档路径)。文档与代码是两份可对照的约束,用对照验证一致性,而不是用交叉引用把两边焊在一起。
- **只描述现状, 不记录历史**: 文档正文只描述系统"当前是什么样",用陈述句写终态。禁止出现"新增了"、"原来是 A 改为 B"、"已废弃"、"临时方案"、日期/版本/PR 号等变更叙述。
- **过程性记录不进 DOC**: SDK 升级、调研笔记、迁移流水、版本对照等过程性叙述不进 `doc/`。这类内容放 GitHub Issue:一类主题一个 Issue,每次发生追加评论。`doc/` 只保留该 Issue 的链接。变更历史属于 git commit、ADR(决策)、database/migrate(表结构)、GitHub Issue(升级/过程账本),不进规格正文。
- **每次修改都是一次重构**: 同步代码时不允许只做加法。改动一处,就要连带删除/合并该主题下过时、重复、矛盾的旧内容,使这一段落读起来像是一次性写成的整体,而非层层叠加的补丁。修改后该主题的文字总量应尽量持平或减少。
- **单一事实源, 不复制**: 同一事实只在一处权威文档描述,其余位置用引用/链接指向,禁止跨文档粘贴同样的内容。发现重复即合并到权威源。文档之间可以互相引用;文档不得引用代码文件,代码也不得引用文档。
- **删除过时内容无需征求同意**: 与代码不符、已无对应实现、被新内容取代的段落,直接删除或改写,不必先询问。
- **每行都要挣得存在**: 删掉套话、显而易见的废话、为凑篇幅的解释。若一句话去掉后信息无损,就去掉。宁缺毋滥。
- **顺带清理是义务**: 无论本次任务是否要求,只要在编辑中读到附近有违反上述原则的内容,顺手修正,不留待"以后"。

## 格式

- 表格字段内容长度超过 50 个字符, 则不使用表格，改用列表形式。
