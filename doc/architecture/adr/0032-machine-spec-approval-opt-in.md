# 0032 — 队列自治的规格阶段:只读审核会话 + opt-in 机器批准 + 可撤销

- **Status:** accepted
- **Date:** 2026-07-31

## Context

ADR-0031 把队列做成了确定性的对账内核,但它只对账**开发**。开启 SDD 的工作区里,一条尚未批准
spec 的 `automate` 意图会永久停在 `blocked_spec_not_approved`:撰写、审核、批准三步全靠人手动
发起。自动化在这三步上是断的。

后果不是「慢一点」,而是**自动化队列的可用范围塌缩到「已经有人写好并批准过 spec 的意图」**。
即便补上自动撰写与审核,最后一步的人工点击仍是端到端自动化的硬卡点。

同时,RM-R22 当时明确写着批准是「单人确认、无撤销」。要引入任何形式的机器批准,这条约束必须
先被正面修订 —— 一个不可撤销的自动批准,一旦误判就无法挽回。

## Decision

把「规格阶段」交给同一个对账内核,并为「机器可以代替人点批准吗」这个问题引入**显式的、每工作区
的 opt-in**。四个决策彼此独立,分别记录。

### 1. `spec_review` 是独立会话类型,不复用 `spec`

审核者读 spec、读仓库源码、读本项目意图,**不写任何路径**;结论通过一个窄接口
(`submit_spec_review`)结构化提交。

**为什么不复用 `spec` kind:** `spec` 携带 spec 目录的写权限(路径级写闸)。复用它等于**静默
授予审核者改写被审文档的能力**,所有权立刻混乱 —— 审核者可以把自己不满意的地方直接改掉,然后
判自己通过。这是权限倒退,不是复用。

因此审核者的 `disallowedTools` 比撰写方**更严**:写类工具在 SDK 层直接切掉(撰写方保留它们是
为了让路径闸能逐路径裁决,审核者根本没有可写位置,无从裁决)。工具层网关再独立 deny 一次 ——
两道,使未来的装配疏漏不会静默递给审核者一支笔。

审核会话**不开放提问**。它是无人值守的队列工作,一个能弹人工提示的审核者会把自动闸门变成静默
停滞。

### 2. 结论绑定内容指纹,而不是绑定时间或会话

每条结论持久化它被产出时所针对的 **spec 内容指纹**。结论有效 ⟺ 指纹等于 spec 当前内容的指纹。

这一个比较替代了一整套失效逻辑:spec 被改写 → 旧结论自动失效 → 下一轮自然重新审核最新内容。
**没有失效扫描任务,没有清理作业,也就没有「忘了跑」的可能。** 同理,一份批准永远不可能停留在
一份已不存在的文档上。

指纹由装配层在每轮对账时从磁盘读出(内核保持纯函数),审核发起时捕获的那一份随会话绑定注入
窄接口 —— 模型自始至终不经手指纹,因此**无法声称审核过它没看到的内容**。spec 不可读时指纹为
`null`,内核按「无法审核」处理,**绝不按「内容为空」处理**。

### 3. 返工有硬上限,超限交回人工

`changes_requested` 使返工轮次原子加一,并携审核理由原文恢复撰写会话。前 3 轮允许返工;第 3
轮返工后的审核仍不通过时不再拉起撰写,创建一次人工待办并在 `queue_decision_log` 记录原因。

无上限往返会烧钱且不收敛。上限之外的判断交给人,是因为「反复三轮仍谈不拢」本身就是一个需要
人介入的信号,而不是一个需要再试一次的信号。

### 4. 机器批准是每工作区的显式 opt-in,默认关闭,且可撤销

**默认关闭。** 缺省、非布尔、遗留值一律读作关闭;只有显式 `true` 打开这条路径。既有工作区升级
后行为**不发生任何变化**。关闭时内核**根本不产生**机器批准动作 —— 不是「产生了但不执行」,
从而不存在被误执行的路径。

**开启后**,`pass` 结论由队列写入 `spec_approved=true`,批准人记为保留常量
`c3:machine-spec-approver`。这个常量**不冒充任何登录 subject**,所以「谁批准的」始终诚实,UI
可以如实区分人工与机器批准。

人工批准与机器批准**共用同一个批准领域能力**,只有调用身份不同。协议 handler 与队列装配层不得
各自复制状态更新规则,否则两者会恰好在最重要的地方漂移(写什么日志、发什么事件、批准人字段
写谁)。

机器批准的落库是**条件事务**:写入时重新校验「未批准、结论为 pass、结论绑定当前指纹、未被人工
否决」。内核基于快照决策,装配层在写入瞬间复核 —— 期间 spec 被改或批准被撤销,则一无所写,
下一轮从新事实重新推导。

**撤销是必须的对偶。** 撤销清除批准与批准身份、写 `spec_unapproved` 审计、广播,意图回到等待
批准。关键在于:撤销**同时否决当前那条审核结论**。没有这一步,开启机器批准的工作区会在下一个
10 秒 tick 把同一条 `pass` 反向覆盖回已批准 —— 撤销按钮将沦为摆设。只有新的有效结论或人工批准
才能解除该否决。撤销**不强杀已运行的开发会话**:它管的是此后的准入,不是已在途的工作。

### 5. 单一 `specReviewAgentId` 槽位,无 sandbox 变体

审核 agent 只有一个设置槽位,语义与 `specAgentId` 完全一致(空串跟随默认且保存后仍为空;非空
但指向已删/禁用 agent 时按 `order_seq` 改写为下一个启用 agent)。

审核是否进入 sandbox **仅由 `sandboxSessionKinds` 是否包含 `spec_review` 决定**。协议里本就不存在
「sandbox 专属 agent 选择」这个维度,新增一个只会制造两个可能不一致的真相。

## Consequences

**得到:** SDD 工作区的自动化不再止步于「有人写好并批准过 spec 的意图」。撰写、审核、返工可以
完全无人值守;是否连最后一步也自动,由每个工作区自己决定。审核结论与返工轮次是持久化事实,
因此整个规格阶段可以像开发阶段一样被确定性重放。

**代价:**

- 审核结论可能与人的判断不一致。人仍是最终把关点 —— 关闭 opt-in 时是事前把关,开启后退化为
  **事后可撤销**。这是开启这个开关所购买的东西,也是它默认关闭的原因。
- 每条意图最多 3 轮返工的 token 开销,外加每轮审核本身。
- 独立的权限域与结构化提交增加了一个会话类型和一组数据契约。这笔账换来的是审核者永远拿不到
  隐式写权,以及结论/返工/批准三者可确定性重放。

**主动放弃的替代方案:**

- **复用 `spec` kind** —— 权限倒退(见决策 1)。
- **审核者直接改稿** —— 所有权混乱:被审文档的作者与审核者合一,审核就不再是审核。
- **无上限往返** —— 烧钱且不收敛。
- **全局默认开启机器批准** —— 对既有工作区是静默的行为突变。
- **不做撤销、接受不可逆** —— 误判无法挽回,风险与收益不成比例。
- **多签** —— 本期不在范围内;它解决的是「一个人不够」,而本变更解决的是「一个人不在」。

## Relation to existing decisions

- **修订 RM-R22** 的「单人确认、无撤销」表述:批准仍是单人确认(不引入多签),但**不再是不可
  撤销的**,且在显式 opt-in 下可由带身份的机器做出。
- **遵循 ADR-0031**:规格阶段是同一个对账内核的一部分 —— 内核只依据事实产生动作,会话启动、
  持久化、事件与广播由装配层执行。规格阶段与开发阶段共享同一套失败隔离(退避 → park)与防自激
  冷却,并按同样的工作区串行原则每轮最多发起一个规格会话。
- **遵循 ADR-0009**(单向边界)与 **ADR-0011**(vendor 中立):审核会话通过与其他 c3 工具相同的
  回环 HTTP MCP 路由暴露其窄接口,claude 与 codex 走同一条路径。
