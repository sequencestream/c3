# 0038 — 依赖闸门判据改为 base 可达

- **Status:** accepted
- **Date:** 2026-08-07

## Context

依赖闸门要回答的问题是「我现在开工,依赖的产出对我可见吗」。在交付出现之前,所有意图都直提主线,「依赖的 PR 合了没有」恰好等价于这个问题,于是判据被写成了后者。

交付把「集成分支」变成了多条(ADR-0036):依赖合进交付分支 A、我在交付分支 B 上开发时,A 的产出对我并不可见,而「PR 已 merged」为真。判据与要回答的问题在此分岔。

同一时期还存在第二个问题:判据有**两份实现**且互不一致。手动路径要求「done + (聚合 PR merged 或依赖分支即主线)」,队列内核只看「聚合 PR merged」。同一批事实,队列可以阻塞而手动放行——一条本就存在的裂缝,交付只会放大它。

## Options considered

- **A. 判据保持「PR merged」,交付另设一套额外规则**:被否决。两套规则并存等于承认「PR merged」不再是判据,却仍让它继续做主判据;跨交付误放行照旧发生。
- **B. 判据改为「依赖的产出在我的 base 上」,按会话的交付上下文分三态求值,收敛为唯一一份共享纯函数**。**采纳。**
- **C. 跨交付判据取「依赖对其所属交付的 PR 已 merged」**:被否决。merged 只证明产出到了**它的**交付分支,不证明到了我的 base;要到我的 base,必须先经主线。
- **D. 定时自动把主线回灌各交付分支,以此弱化跨交付等待**:被否决。后台静默改共享分支、失败无人看,违背 never-auto-merge 立场。

## Decision

- **判据是「依赖的产出在不在我的 base 上」,不是「依赖的 PR 合了没有」。**
- **闸门的上下文是「会话的交付上下文」,不是意图。** 多交付意图无法唯一决定 base,因此启动写入会话时必须定下 `deliveryId`:0 关联为无上下文、恰好 1 个自动带入(唯一事实,不算猜测)、≥2 个必须显式携带否则拒绝。解析结果随会话记录持久化,resume 复用而不重新猜测。
- **三态口径**:同交付看「依赖对该交付的 PR 行是否 merged」(按交付看,不看聚合);跨交付看「依赖所属交付是否 `delivered`」,多关联时全部非当前交付均 `delivered` 才放行;无上下文或依赖无任何关联时沿用原判据(done + 聚合 merged 或分支即主线)。
- **判据只有一份实现,放在 `@ccc/shared` 的领域纯函数里。** 内核不得 import features(ADR-0009),共享层是让手动路径与队列内核引用同一实现的唯一干净位置;代价是输入必须全部以事实快照传入,归约由各读取方在自己的边界完成。
- **跨交付等待从小时级变周级,是语义正确性的必然代价。** 缓解手段是可解释闸门 + 强制放行逃生口,**不是放松判据**。
- **依赖闸门是建议,可被知情放行。** 强制放行一次性、不持久化、只跳过依赖闸门、需二次确认并展示风险说明、留 `intent_logs` 审计;自动化队列不提供——无人值守路径不替人做判断。
- **worktree 基线是 `origin/<交付分支>`,且已存在的 worktree 一律不自动重建。** 基线不符时阻塞启动并给两个显式出口(干净才允许安全重建 / 人工确认后合入)。这类阻塞**不在逃生口范围内**:依赖闸门关乎合并成本,基线不符关乎会不会丢工作。
- **交付状态是调度资格闸门。** `verifying / verified / delivered / cancelled` 期间其关联意图不再产生新的写入会话——验证期间继续合代码等于验证结论作废;手动入口与队列共用同一判据,不留「自动化被拦、手动放行」的裂缝。

## Consequences

- 队列路径在无交付分支上从「只看聚合 merged」放宽到与手动路径一致:依赖分支即主线但 PR 未 merged 时,原队列阻塞、现在放行。这是「两条路径结论一致」的必然结果。
- 旧客户端不带 `deliveryId` 启动:单关联与无关联行为不变;多关联意图从「可启动」变为「明确报错要求选定」——预期语义收紧,不是回归。
- 跨交付依赖的等待窗口显著变长。可解释文案必须指明「依赖在交付 X,X 未合入主线」并可跳转,否则用户只会看到一个无从下手的阻塞。
- 「同步主线」把冲突处置时机前移,使 `verified → delivered` 的最终合并接近 fast-forward;它永远由人触发,冲突原样浮出。
- 判据的输入面变宽(交付关联、按交付的 PR 状态、交付状态快照),队列事实投影相应扩展;投影失败按既有 snapshot 失败处理,不盲启动。

## Compliance

- `shared/src/dependency-gate-model.ts` 是判据的唯一实现;`server/src/features/intents/dependency-gate.ts` 与 `server/src/kernel/queue/reconcile.ts` 都只调用它,任何一方重述判据即违规。
- `shared/src/delivery-gate-model.ts` 是「交付是否禁止新写入」的唯一实现,手动准入与队列共用。
- 会话交付上下文持久化于 `intent_sessions.delivery_id`(见 `database/tables.md`)。
- `server/src/features/intents/worktree-baseline.ts` 只做检测,不执行修复;两个出口在 `repair_intent_worktree` 里显式执行。
- 三态与两条路径一致性由 `shared/src/dependency-gate-model.test.ts`、`server/src/features/intents/dependency-gate.test.ts`(「两条路径结论一致」)与 `scripts/e2e/e2e-dependency-gate-test.mjs` 覆盖。
