# 0041 — worktree 基线不符是提示,不是闸门

- **Status:** accepted
- **Date:** 2026-08-09

## Context

worktree 基线检查回答的是「这个目录里的代码,是不是长在这次改动该落的分支上」。判据是一次祖先测试:已存在的 worktree 的 HEAD 是否包含刚 fetch 到的 `origin/<意图基准分支>`。

这条判据把两种成因完全不同的情形压成同一个结果:

- **目录当初就建在错误基线上** —— 罕见,且属于创建路径的缺陷;
- **基准分支在目录创建之后推进了** —— 常态,团队每合一个 PR 就发生一次。

祖先测试在原理上分不开这两者:两种情形的提交图同构,都是「base 上有 worktree 缺的提交」。而阻塞对两者是同一个代价 —— 用户在意图页被一个修复弹窗挡住,只能选重建(可能丢工作)或合入(改写自己的分支)。

第二种情形本身并不妨碍开发:在稍旧的基线上写代码完全成立,分歧真正需要处置的时点是 PR 合并 —— 那里有 forge 的冲突提示与人的判断。用一道启动闸门去提前处理一件在合并时才成立的事,拦下的绝大多数是正常工作。

## Options considered

- **A. 维持阻塞** —— 被否决。它按最罕见的成因给所有情形定价,日常代价远大于收益。
- **B. 只放行「落后」、仍阻塞「建错基线」,以 worktree 当前分支是否为该意图自己的分支作判据** —— 被否决。这是相关性而非因果:目录建在错误 base 上、随后照常切到意图分支开发,同样满足该判据,守卫形同虚设,却仍留着一道会误伤的闸门。
- **C. 记录 worktree 创建时的基准分支名,据此区分两种成因** —— 被否决。它能分开两者,但要为一个罕见缺陷引入新的持久化事实与迁移;缺陷本身应在创建路径修,而不是在准入路径侦测。
- **D. 检测保留、结果降级为提示,启动照常;两个修复动作原样保留为人工动作。** **采纳。**
- **E. 彻底删除检测** —— 被否决。「意图关联交付后基准换成交付分支」这类真实的基线漂移就此无人发现,且两个修复出口失去触发它们的语境。

## Decision

- **基线不符不拦启动。** 四类会话(意图沟通 / 规范撰写 / 规范评审 / 开发)与 resume 一律照常启动,自动化队列同样不再因此记失败。
- **它是一条陈述事实的提示**,随启动结果推给发起连接,携带期望基线(分支 + 交付标题)、worktree 当前实际所在(分支 + HEAD)与「此刻能否安全重建」。测不出来(无远端引用、worktree 不存在、祖先判断无结论)时连提示都不产生。
- **两个修复出口不变,仍然只由人触发**:安全重建要求无未提交改动(执行前再查一次),合入是在 worktree 内显式 merge `origin/<基准分支>`,冲突原样浮出。c3 从不自动重建、从不暗中 merge、从不静默丢工作 —— 这条底线与本决策无关,不因降级而松动。
- **基线落后的处置时点是 PR 合并**,不是会话启动。

## Consequences

- 基准分支推进后不再需要任何人工动作即可继续开发;这也意味着一个真正建错基线的目录不再被拦住,它会一路开发到 PR 合并时才暴露成冲突。这是本决策自愿承担的代价:两种情形分不开,就按常见那种定价。
- 没有了「被拒 → 给出口」这条路径,重建 / 合入两个动作改由意图详情常驻的提示条提供,提示不阻断详情页的任何操作。
- 数据安全的保证从「拦住启动」转移到「两个动作都要人点」——后者才是真正防止丢工作的那一环,前者只是它的触发器。

## Compliance

- `server/src/features/intents/worktree-baseline.ts` 只做检测并返回事实,不产生任何拒绝码。
- 会话启动的失败面只剩「目录创建失败」;`session-worktree.ts` 的 `IntentWorktreeFailure` 不再承载基线语义。
- 提示经 `intent_worktree_baseline_notice` 上线;修复仍只经 `repair_intent_worktree`。
- 规则正文见 intent-management 的 RM-R42。
