# 0045 — 工作区记忆:一类被允许的本地持久化 + work session 写入免确认

- **Status:** accepted
- **Date:** 2026-08-19

## Context

c3 的安全需求 SEC-2 曾断言「c3 不做持久化存储,不把工具的输入/输出记录到磁盘日志」。前半句早已与
现实不符——意图、交付、讨论、配置、审计全部落在 `~/.c3/c3.db`;后半句仍然是真正要守住的红线。
一条把两件事绑在一起的需求,既挡不住任何东西,又让每一次合理的持久化都要绕过它。

与此同时,跨 run 的知识无处安放。用户在多个 work session 里反复口头表达的偏好、验证过一次的项目
约束、踩过的坑,仓库自身无法自证,写进 `CLAUDE.md` 又违反那份文件的定位(它只承载「任何工具都能重新
推导」的事实)。结果是每个新 work session 都相当于失忆重来。

需要一次裁决同时回答三个问题:哪一类持久化被允许、这类写入要不要每次弹窗、以及哪些 agent 有资格
产生这类写入。

## Options considered

- **A. 记忆写进仓库内的 markdown** —— 被否决。它会污染代码库,进 PR diff 与评审,并且天然跨工作区
  泄漏(仓库可以被多人共享,记忆是本机用户的)。
- **B. 记忆放在意图/交付台账里派生** —— 被否决。台账记录的是**做过什么**,记忆记录的是**结论**。
  从台账反推用户偏好需要语义判断,而这正是本期明确不引入的东西。
- **C. 每次 `memory_write` 弹权限确认** —— 被否决。记忆维护是高频、低风险、可撤销的动作,逐次确认会
  把用户训练成不读就点同意,反而削弱其它工具的确认价值。
- **D. 不限定 session 类型,所有 agent 都能写** —— 被否决。讨论/意图/规格类 agent 产出的是**合成
  观点**,不是用户共识;让它们写入会使「工作区事实」在无人察觉处被机器意见污染。
- **E. 写入前用 LLM 判断是否与已有记忆矛盾** —— 被否决。它把一个不可审计的语义判断放进写路径;本期
  只保留一条确定性规则(归一化 title 相同即同一条)。
- **F. 到达容量上限时淘汰最旧记忆** —— 被否决。静默淘汰用户说过的话,是这套存储最不能出现的行为。

## Decision

### 允许的持久化类别

SEC-2 的终态规则改为:**c3 可以持久化被显式选择的、结构化的运行数据(工作区记忆即其一),但不得
把原始 prompt、对话转录、代码或工具输入/输出作为记忆或磁盘日志持久化。**

工作区记忆属于被允许的一侧,依据是它同时满足:

- **结构化字段,不是自由转储** —— 封闭的 `type` 枚举 + `title` + `content` + 可空 `subject`,没有任何
  一列可以放代码、命令、提示词或工具输入输出。
- **工作区绑定** —— 每次读写都以 `workspace_name` 为边界,`subject` 只分组不扩权。
- **输入上限** —— 单条 `content` ≤ 2000 个 Unicode 码点,单工作区 ≤ 500 物理行。超限显式报错。
- **写入即拒绝凭据与产物形状** —— 集中的拒绝规则挡下私钥块、bearer/访问令牌、凭据赋值,以及代码围栏、
  工具调用/返回框架与角色转录行;拒绝信息从不回显命中的内容。
- **软删 + 延迟物理清理** —— 删除是状态变更,`superseded`/`deleted` 行满 30 天才被物理删除。
- **角色排除** —— 只有 `work` session 能拿到这两个工具。

这几条不是实现细节,而是这条裁决可被复核的凭据:任何一条被拿掉,记忆就不再属于「被允许的持久化」。

### work session 的记忆写入免确认

`mcp__c3__memory_search` 与 `mcp__c3__memory_write` 由标准权限门直接放行,不产生 `permission_request`
线消息、不写用户介入记录、不走共识。

理由是这两个工具的风险面已经被上面的约束压到确认对话框能提供的价值之下:检索是只读的;写入受封闭
字段、长度与容量上限约束,且在本机可逆(软删可撤、同名重写即覆盖、物理删除延迟 30 天)。逐次弹窗只会
制造点击疲劳。

**免确认不等于可用。**能不能调用由 run 生命周期的工具面决定,与权限门是两件事。

### 工具面由 `sessionKind === 'work'` 正向选中

work session 的 MCP profile 用正向谓词选中,不能写成「其它 profile 都没匹配」。反向写法会让每一个
将来新增的 session kind 默认继承记忆工具——首当其冲的就是讨论 agent,而排除它们正是选项 D 的裁决。

`intent`、`spec`、`spec_review`、`discussion`(调研会话与编排的逐 agent 会话)因此都拿不到这两个工具。

### 刻意排除

- **不做启动时记忆注入**,不自动读。记忆是 agent 主动检索的对象,不是隐式上下文。
- **不做 LLM 压缩、FTS5、向量检索与语义矛盾检测。**真正互斥的两条用不同 `title` 表达,系统两条都保留。
- **不加 `confidence` / `expiry` / `last_read_at`**,因此也无法实现「90 天未引用即清理」。
- **不新增协议分区、HTTP 路由或外部 MCP 暴露**,复用既有 event MCP 回环路由。
- **不做浏览器管理界面**,不从意图/交付台账、仓库文件或厂商会话库回填任何历史记忆。

## Consequences

免确认换来了记忆维护的可用性,代价由 work-only 暴露面、严格的输入拒绝、可见回执、软删与延迟清理共同
承担;这条例外写在这里,而不是放宽默认权限模型本身。

记忆不是密钥库:形状检测挡得住常见凭据,挡不住任意散文,领域文档必须明说这一点。字面检索会漏掉同义
表述,调用方的补救是先列目录再换词,系统不会自行扩大范围。

回收期内被删除的记忆仍占容量,容量满时新条目被拒——这是刻意的:缩短可恢复性或淘汰另一条记忆,都比
让用户看到一条明确的错误更糟。

将来的二期若要放开写入角色,应引入 `confidence` 字段并默认 `unverified`,而不是撤销本裁决的角色排除。
