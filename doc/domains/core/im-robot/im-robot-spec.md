# im-robot — 规格

实体定义见 [im-robot-models.md](im-robot-models.md);物理接线见 [im-robot-design.md](im-robot-design.md)。

## 一条消息的判定链

平台投递一条消息后,它要通过下面每一步才会变成一次回合。任何一步不通过即静默丢弃——群里不会看到
任何反应,因为「这条消息不归我管」本来就不该产生噪音。

1. **机器人仍然启用。** 每条消息都重新读取配置:管理员可能在连接建立后收紧了策略或停用了它。
2. **响应面。** 群消息:`requireMention` 为真时必须 @机器人;`chatAllowlist` 非空时群必须在其中。
   单聊:`dmMode` 为 `disabled` 即不响应,为 `allowlist` 时发送者必须在名单内。
3. **可读性。** 只处理文本消息。图片、文件、卡片一律跳过——看不到内容就没有可回答的东西,猜测只会
   产生一个用户没问过的回答。来自其它机器人的消息同样跳过,否则两个机器人会互相说个不停。
4. **不是重复投递。** 同一线程上同一消息 id 已经处理过即丢弃。
5. **该线程空闲。** 见下。

## 一条线程一次只跑一个回合

同一 `(robotId, threadKey)` 上的回合严格串行。线程忙时到达的新消息**不排队也不并发**,而是立刻回一句
「上一个还在处理」——排队会让人以为消息丢了,并发则会让两个回合争抢同一个会话。

不同线程之间不设并发上限,与 c3 在别处的立场一致。

## 每条被接受的消息都以回复或审计原因结束

一次静默丢弃的回答比一次失败更糟:群里的人分不清「失败了」和「被无视了」。因此进入回合的消息一定
得到某种回复:

- 回合正常结束且有文本 → 发出该文本
- `blocked` → 告知需要人工授权,请到 c3 中继续
- `timeout` → 告知超时已中止
- `guard_refused` → 告知内容疑似含凭据已拦下
- 其它失败 → 告知出错,请到 c3 查看

无论哪种,都写一行审计。

## 外发授权

启用一个机器人就是授权数据离开本机,因此它由四条共同约束(ADR-0046),缺任何一条本裁决即失效:

- **默认停用。** 创建即停用,不存在「创建并启用」的一步操作。
- **启用前确认。** 一次不可跳过的确认,逐条列出会被发往第三方云的内容范围;确认时刻被记录。
  **服务端在启用时校验它**——前端少弹一个框不能让机器人通过。
- **仅管理员。** 创建、修改、启用都是外发授权决策。
- **逐次审计。** 每次外发落一行,只记元数据。

启用另需一个可连接的凭据;缺凭据或缺确认,启用被拒绝并给出对应原因。停用永远允许。

## 允许外发的内容

**只有一轮回合结束时的最终 assistant 文本。** 工具调用、工具结果、中间推理、文件内容、会话转录一概
不外发。这是结构性的:承载回合的观察者只累积 assistant 文本,其余线事件根本不进外发路径。

发出前还有两道处理:

- **凭据形状守卫。** 命中即不外发,改回固定的拒绝说明,以 `guard_refused` 落审计;拒绝信息从不回显
  命中的内容。它复用的是凭据规则,**不含**记忆域的产物规则——一个关于代码的回答理应带代码块。
- **长度截断。** 超过平台上限时截断并**明说被截断了**,完整内容留在 c3 会话里。

## 无人值守会话不得挂起

群里没有人能回答授权对话框。因此机器人回合跑在一个专属的权限门下:

- 读类工具放行
- **面向人的交互工具(提问、计划确认)直接拒绝**——放行等于制造一条永远不回复的消息
- 写/执行类只在该机器人的冻结白名单内放行,否则拒绝
- 其余一律拒绝(默认拒绝是结构性的)

对结构上不支持逐工具审批的厂商,启动期策略即门禁,不在审批桥上等待。此外回合本身有墙钟上限,
且一旦观察到授权请求即刻以 `blocked` 收敛,不等待。三者构成三重防线。

## 工具权限网格

机器人回合能用哪些工具,由创建/编辑时勾选的权限网格决定。网格按当前厂商加载工具清单
(SDK 内建工具 + c3 自己的 MCP 工具),按「只读 / 写入」两组呈现,带全选与全清。两条原则:

- **创建默认只读。** 新建时只勾只读类工具,写入/执行类不勾,`network-access` 关闭。
- **编辑保持原样。** 编辑时回读已存的白名单并原样勾选;清单加载失败或为空时网格显示空态,
  但**不会把已保存的白名单清成空网格**。

**切换厂商会清空上一个厂商的勾选**——一个厂商的工具名不会残留到另一个厂商下。清单加载失败不提供
自由文本兜底:网格没有文本框。

### `network-access` 伪条目

`network-access` 不是一个工具,而是随白名单一起存储的能力开关(同样出现在 allowlist 里),永远不进入
门禁/放行集合,也不参与全选/全清。语义:

- **仅 Codex + workspace-write 沙箱生效**:打开它只允许 codex 的 shell 命令出网。
- 它**不授予 shell 本身**,也不启用 web 搜索。
- 默认关闭。只读沙箱下开关置灰并解释(该沙箱无条件禁网);切回可写沙箱时,已存值保留。
- 没有网络旋钮的厂商(claude 等)静默忽略——不渲染开关,残留的存量值不影响启动也不扩大能力。

### 机器人回合的沙箱推导

Codex 原生沙箱模式**只**由 SDK 本地写/执行工具决定:勾了 `shell` / `apply_patch` 之一即为
workspace-write,否则只读。勾选 c3 MCP 写工具(如 `mcp__c3__save_intents`)**不**算——它跑在 c3
服务端自己的域守卫之后,绝不能成为打开可写沙箱(进而打开网络边界)的理由。

### c3 MCP 工具按回合绑定

勾选的 c3 MCP 工具按线程经回环 HTTP MCP 绑定到回合工作目录(`~/.c3/robots/<name>/`),只暴露勾选的
子集:未勾选工具既不出现在 tools/list,直接调用也被拒绝。c3 MCP 不得跨出机器人自身运行根目录——
`find_*` 返回空、`view_*` 未找到都是预期,而不是错误。机器人不与任何项目或线程绑定。

## 与工作区的关系

机器人不属于任何工作区。它在自己的目录 `~/.c3/robots/<name>/` 中运行,该目录不进工作区注册表,
因此:不出现在工作区切换器、不出现在会话页、其 run 不会唤醒为本机开发流程配置的自动化
(机器人会话种类需被自动化显式点名才参与匹配)。

一个机器人的多条线程共享同一个工作目录。当前只保证同线程串行,因此跨线程并发写同一目录是可能的——
这正是预设权限默认只读的原因之一。
