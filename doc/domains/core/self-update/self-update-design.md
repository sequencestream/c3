# self-update — 领域实现设计

## 1. 定位

c3 以单二进制分发，装在哪由用户决定。发现新版本很容易（后台检查已经在做），装上却要用户回到终端跑 `c3 upgrade` 再跑 `c3 restart`——大多数人不会做，于是一台机器上的 c3 停留在装那天的版本。

self-update 领域把「检查 → 下载 → 重启生效」在服务端串成一条链：后台自动把最新发行包下载并校验到暂存区，控制台顶栏给出「重启以更新」，管理员点一下就跑在新版本上。

## 2. 范围与边界

范围：能否自更新的判定、后台下载与完整性校验、暂存区生命周期、二进制替换的时机、按运行形态选择重启方式、跨重启的状态对账。

边界：

- **不重造升级内核**。版本事实、发行包解析、传输与 sha256 规则、平台替换策略全部复用 `server/src/upgrade-core.ts` 与 `server/src/upgrade.ts`，与 `c3 upgrade` 同一套。
- **不改 `c3 upgrade` 的契约**。CLI 仍只替换磁盘上的二进制、从不重启；自更新是它之上的编排层。
- **不接管桌面壳**。桌面版按整包升级（壳与 sidecar 成对），单独替换 sidecar 会破坏 bundle 签名，所以桌面形态下本领域整体让位（见 `doc/non-functional/release.md`「桌面渠道」）。
- **不越过包管理器**。装在 Homebrew 前缀下的二进制由 `brew upgrade` 管。
- **不做降级、不做版本选择**。目标恒为最新发行版。

## 3. 能力门

自更新对运行形态挑剔，判定 fail-closed，按「多根本」排序，命中即止：

| 判定                       | reason            | 含义                               |
| -------------------------- | ----------------- | ---------------------------------- |
| `C3_MANAGED_BY=desktop`    | `desktop-managed` | 桌面壳拉起的 sidecar，更新由壳负责 |
| dev 版本或解释器运行       | `dev-runtime`     | 没有单一二进制可换                 |
| 可执行文件位于包管理器前缀 | `package-manager` | 交给该包管理器升级                 |
| 可执行文件所在目录不可写   | `not-writable`    | 换不动                             |

不可自更新时顶栏退回纯提示，外链发行页，由用户按自己的安装方式升级。

## 4. 状态机

服务端持有**唯一一份**状态，单向推进：

```text
idle → downloading → verifying → ready → applying
  ↑         └────────────┴─────────┴──→ failed（可重试）
```

- `downloading` 由后台检查发现新版后自动进入，无需用户点击；下载中重复请求合并到在途任务。
- `verifying` 是字节收齐、正在与发行包的 `.sha256` 对账的瞬间。
- `ready` 意味着**包已校验并解包成可运行的二进制**，但安装位置仍是旧版本。
- `applying` 是替换已发生、重启已移交，连接即将断开。
- `failed` 保留失败分类（`network` / `no-artifact` / `checksum` / `unpack` / `replace` / `relaunch` / `unknown`）与英文诊断串，可重试。

两条不变量让它可以无人值守地跑：

- **下载不改变任何要紧的东西**。`ready` 之前不碰安装位置的二进制，磁盘与运行中的进程始终一致，坏包或中断只花带宽。
- **`ready` 必须是可运行的**。字节数与摘要都对上、解包出内层二进制，才算就绪。

失败与取消一律清空暂存区，绝不把半成品留到安装阶段。

## 5. 暂存区

`<c3Home>/update-staging/`，随 `--db` 迁移，两个实例互不干扰。全部是普通文件——重启助手是独立进程，不该为读一条记录去开 SQLite。

- `staged.json`：**存在即就绪**。它在下载校验解包全部通过后最后写入，写法是临时文件 + rename，崩溃不会留下半份。记录里带 `execPath` 与 `version`，因此换了安装位置或版本对不上的旧记录会被识别为无效。
- `apply-failure.json`：助手回传失败的唯一通道——请求替换的那个服务端此时已经不在了。下次启动读出、展示、清除。

## 6. 重启：按运行形态分策略

`c3 restart` 面对的是**别的**实例，可以直接停再起；一个实例重启**自己**不能——它活不过自己发出的那条命令。因此策略按谁拥有这个进程来分：

| 形态                | 策略                 | 谁替换二进制 | 要点                                                                                                             |
| ------------------- | -------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------- |
| systemd 服务        | `systemd`            | 本进程       | `systemctl --user restart --no-block`：`systemctl` 子进程在本单元 cgroup 内会被一起杀掉，只有入队的 job 活得下来 |
| launchd 服务        | `launchd`            | 本进程       | plist 是 `KeepAlive`，干净退出本身就是重启                                                                       |
| `--daemon` 后台进程 | `assistant-daemon`   | 助手进程     | 后继进程必须由别人拉起，否则与自己抢端口                                                                         |
| Windows 计划任务    | `assistant-schtasks` | 助手进程     | `/End` 会杀掉自己，`/Run` 就再也执行不到                                                                         |
| 终端前台            | `inline-foreground`  | 本进程       | 释放端口后就地派生后继进程，继承同一终端与进程组（Ctrl-C 仍然有效）；副作用是 shell 提示符会提前返回             |

助手是同一个可执行文件的隐藏子命令 `c3 update-apply --wait-pid <pid> --update-dir <dir> --form <daemon|schtasks>`，完全脱离父进程：等旧 pid 退出 → 替换二进制 → 按形态拉起 → 清理暂存区。**旧进程没退出就不替换**，否则后继进程会撞上仍被占用的端口。

## 7. 失败与回滚

替换本身沿用升级内核的既有保证：POSIX 走同目录临时文件 + 原子 rename（并先跑一次 `--version` 自检），Windows 走「运行中的 exe 改名让位」，rename 之前的任何失败都让原二进制毫发无损。

在此之上：

- 替换失败 → 旧版本仍可启动，状态回到 `failed`。
- 替换成功但拉起失败 → 新二进制已装好，失败信息明确指出「重启 c3 即可用」，不谎报成功。
- 助手场景下这两类失败写进 `apply-failure.json`，下次启动如实呈现。

## 8. 权限与可见性

下载与重启都是**管理员**动作：一次重启会断开所有已连接会话，中断运行中的智能体。状态本身则广播给所有连接——即将重启这件事与每个开着控制台的人都有关，只是只有管理员能触发。控制台对非管理员只展示「已就绪，等待管理员重启」。

## 9. 启动对账

进程启动时扫一遍暂存区，三种输入三种结果：助手留下的失败 → 呈现为 `failed` 并清除；包对应的版本就是当前正在跑的版本（或对应另一个安装位置）→ 说明这次重启已经生效，清理；包对应更新的版本 → 保持 `ready`，跨重启存活。
