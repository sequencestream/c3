# 从需求到意图（From Requirement to Intent）

在 AI 软件工程时代，表达"我们要做什么"的单元正在从需求转变为意图。下面先讲清楚这一转变，再介绍意图在 c3 中的具体形态和使用方式。

---

## 一、从需求到意图

### 背景：传统需求的问题

传统软件工程以需求（Requirement）为出发点：产品经理写文档，开发者读文档、拆任务、写代码。这套流程在"人写代码"的时代运转了几十年，但存在几个问题：

1. **只说"做什么"，丢了"为什么"。** 需求文档往往是功能清单（"增加导出按钮"），至于为什么做、权衡过哪些方案，这些上下文只留在会议室和聊天记录里。开发者拿到结论而非意图，遇到边界情况只能猜或反复追问。
2. **靠人拆解，拆完就静止。** 需求经"史诗 → 特性 → 用户故事 → 任务"层层人工拆解，拆完冻结在工单系统里，与代码、测试、文档各自演化，久而久之"工单说的"和"代码做的"渐行渐远。
3. **完成标准模糊，验收靠人肉。** 很多需求没有可验证的完成标准，验收依赖测试人员经验；测试、文档常被拆成独立任务，排期时被砍掉。
4. **需求与执行之间有一道人力鸿沟。** 需求写得再好，也要人来理解、翻译成代码，这既是成本，也是失真的主要来源。

这些问题在人写代码时是可以容忍的摩擦——反正都要人来消化需求。但当 AI 智能体成为执行主体，这套体系就不够用了。

### 意图是什么

AI 智能体（agent）可以直接从一段自然语言出发去阅读代码、规划方案、修改文件、运行测试。执行不再是瓶颈，瓶颈变成了"你到底想要什么"能否被精确、完整、可验证地表达出来。

这就是意图（Intent）登场的原因。意图不是换个名字的需求，而是为"AI 执行、人把关"这一分工设计的表达单元：需求面向人，靠人补全上下文、拆解任务、判断完成；意图面向智能体，必须自带上下文（Why）、边界（What / Non-goals）、权衡（Trade-offs）和可验证的完成标准（Acceptance），因为执行它的智能体只有你给它的文本。

意图的产生过程也不同：不是人独自写文档，而是人与 AI 对话共创——你说出想法，AI 帮你澄清、补全、拆解成一组大小合适、依赖清晰的意图条目，最后由你确认才生效。

### 意图内容的五个维度

意图内容的核心是五个维度：Why、What、Trade-offs、When、Acceptance。这是意图能被智能体正确执行、被人可靠验收的最小完整信息集——除 When 可在无外部时机约束时省略外，缺了任何一个维度，执行时就得靠猜。

下面用同一个例子贯穿说明："给用户列表增加 CSV 导出功能"。

#### Why —— 为什么做

回答的问题：这个意图解决什么问题？不做会怎样？

Why 是传统需求最常丢失的部分，却是智能体做技术决策时最重要的依据。同样是"导出 CSV"，Why 若是"运营每周手工整理用户数据做报表"，智能体会倾向贴合报表习惯的列和格式；Why 若是"满足合规审计的数据留存"，则完整性和字段保真压倒易读性。Why 决定了实现过程中无数取舍的方向。

> ❌ 增加导出功能。（没有 Why，遇到分歧只能猜）
>
> ✅ 运营团队每周需将用户列表导入 Excel 做增长分析，目前靠人工复制粘贴，300+ 行时经常出错、耗时约 1 小时。

#### What —— 做什么、边界在哪

回答的问题：交付的能力是什么？范围到哪为止？哪些明确不做（Non-goals）？

What 描述可观察的行为变化，而非实现细节（不列文件路径、不指定函数名——那是智能体的工作）。边界同样重要：明确不做什么，防止范围蔓延（scope creep）和验收时的期望错位。

> ✅ 用户列表页新增"导出 CSV"按钮，导出当前筛选条件下的全部用户（不只当前分页），包含姓名、邮箱、注册时间、状态四列。不做：Excel（.xlsx）格式、定时自动导出、导出历史记录。

#### Trade-offs —— 权衡与取舍

回答的问题：有哪些备选方案？为什么选了这个、放弃了那些？接受了什么代价？

传统需求只给结论，权衡过程留在会议室里；后来的维护者看到"奇怪"的设计时无从判断是深思熟虑还是历史包袱。把权衡写进意图，智能体遇到相关分叉时就能沿既定方向走，而不是重新发明一个与你决策相悖的方案。

> ✅ 大数据量导出考虑过后台异步任务 + 邮件通知，但当前用户量级（<5 万行）下同步流式导出即可，避免引入任务队列的复杂度；接受的代价是超大筛选结果下请求耗时较长，超时上限设为 60 秒。

#### When —— 外部时机

回答的问题：有没有外部的时间约束或触发条件？比如截止时间、上线窗口、必须先就绪的外部状态。

When 只记录外部时机：触发条件、截止时间（deadline）、依赖的外部前置状态。它是五个维度中唯一可省略的——没有外部时机约束时不必硬写。

> ✅ 运营的月度增长报表在每月 1 日生成，导出功能需在本月底前上线；"状态"列的对外命名需等运营侧确认枚举值后才能定稿。

#### Acceptance —— 可验证的完成标准

回答的问题：满足什么可观察的条件才算"做完了"？

Acceptance 对"AI 执行、人把关"分工最关键。它必须是可验证的行为清单，而不是"功能正常"这类空话——开发智能体用它自检，独立的完成判定参照它判断，你验收时逐条核对即可，无需读代码。按"一个目标一个意图"的原则，配套测试和文档的同步也写在这里。

> ✅ 示例：
>
> - 在用户列表页应用任意筛选后点击导出，下载的 CSV 行数与筛选结果总数一致；
> - CSV 用 UTF-8 with BOM 编码，Excel 直接打开中文不乱码；
> - 空结果导出得到仅含表头的文件，而非报错；
> - 导出接口有集成测试覆盖上述三种情况；
> - 用户手册的"列表操作"一节补充导出说明。

#### 五个维度小结

| 维度           | 回答的问题         | 缺失的后果                             |
| -------------- | ------------------ | -------------------------------------- |
| **Why**        | 为什么做           | 智能体在取舍分叉处只能瞎猜方向         |
| **What**       | 做什么、不做什么   | 范围蔓延或货不对板                     |
| **Trade-offs** | 为什么这样做       | 被否掉的方案被重新发明                 |
| **When**       | 受什么外部时机约束 | 错过截止时间，或在外部条件未就绪时白做 |
| **Acceptance** | 怎样算做完         | 无法判定完成，验收靠人肉读代码         |

> 小提示：你不需要一开始就把五个维度写全——用一两句话说出想法，AI 会结合项目代码向你提问、补全，最终生成覆盖五维的意图供你确认。

### 意图的特点

- **自带上下文，独立可执行。** 智能体不需要场外信息就能开工，验收的人不需要读代码就能判断。
- **粒度合适（right-sized）。** 拆到"一次可完成、可验证"的大小，既不是大而空的史诗，也不是碎成一地的子任务。
- **一个目标就是一个意图。** 代码、配套测试、配套文档折叠进同一个意图，绝不拆成独立的"补测试""更新文档"工单，从机制上杜绝三者失去同步。
- **完成标准可验证。** Acceptance 写的是可观察的行为，开发结束后可依据结论和代码变更独立判定。

### 从需求转向意图的好处

1. **表达一次，全程复用。** 意图的上下文同时服务于确认它的你、撰写规范的智能体和实现它的开发智能体，无需口头反复交代。
2. **人的精力用在刀刃上。** 人不再逐行写代码，而是在关键节点把关：确认意图、批准方案、审批敏感操作、验收结果。
3. **可追踪、可审计。** 每个意图关联着沟通记录、规范文档、开发会话、代码分支和 PR/MR，整条链路有据可查。
4. **天然支持并行与自动化。** 依赖图 + 工作区隔离让多个意图并行开发互不干扰；自带完成标准，才使"自主开发 → 判定完成 → 提交 → 下一个"的自动化循环成为可能。
5. **代码、测试、文档不再漂移。** "一个目标一个意图"从源头保证三者作为整体被实现和验收。
6. **降低翻译失真。** 意图在项目代码的语境中由人与 AI 共同澄清，比人凭记忆写的需求文档更完整、更少歧义。

## 二、c3 中的意图及使用方式

c3 通过意图驱动编码工作：把需求、规范、测试、文档折叠进同一个目标，实现"一个目标一个意图"。详见 https://github.com/sequencestream/c3。

### c3 中意图的构成

在 c3 中，意图落地为工作区一条结构化记录，主要字段如下：

- **标题（title）** — 一句话说清这个意图要达成什么
- **英文短标题（shortEnTitle）** — 简短的 ASCII 标题，用于派生 Git 分支名 / worktree 目录名
- **内容（content）** — 完整描述，覆盖第一部分所述的 **Why / What / Trade-offs / When / Acceptance** 五个维度。草稿与待办可直接改正文；进行中及之后锁定
- **优先级（priority）** — `P0`–`P3`，P0 最高，决定队列开发顺序
- **影响范围（impactLevel）** — `L1`–`L5`，与优先级正交：优先级回答何时做，影响范围回答做错了波及多远。高影响强制规格先行且禁止机器批准；低影响在未显式覆盖时默认 `fast`
- **规格模式（specMode）** — `sdd`（必须先批准规格）/ `fast`（可先开发，超阈值再反向补规格）/ 空（继承工作区）。规范或开发起步后不可改
- **模块（module）** — 由沟通智能体从标题/内容推断，仅供展示
- **状态（status）** — `draft` → `todo` → `in_progress` → `reviewing` → `done` / `cancelled`。`reviewing` 表示代码已提交、PR 未了结
- **依赖** — 同工作区内的有向边。闸门看前序产出是否已在本意图基线上，不是看前序 PR 是否合并；手动启动可一次性放行依赖这一道
- **自动化标记（automate）** — 是否进入该工作区的意图队列；勾选只给候选资格，不启动队列、不跳过闸门
- **基准分支** — 创建时落库的快照，之后不追随工作区主线推进。PR 目标与 worktree 基线读同一个值

每条意图还可关联沟通会话、规格撰写 / 审核会话、工作会话、PR 行、WorkNote 与交付。

### 前置条件

已完成 [c3 入门指南](c3-get-start.md) 中的安装与启动，并创建了指向你项目目录的工作区（Workspace）。

### 创建意图·方式一：直接新建（主入口）

1. **进入意图视图，点击 +。** 弹出新建意图对话框。
2. **选定基准。** 互斥两支：一条工作区分支（默认预填主分支），或一个仍可写入的交付（分支已就绪，且处于规划 / 集成中）。
3. **写下想法。** 内容非空才会提交。服务端一次请求里登记意图、记下基准，并启动该意图的沟通会话，把这段话当作第一轮输入——不必再开一次会话把背景重讲一遍。内容留空只登记、不起会话。
4. **让沟通智能体细化。** 沟通智能体是只读的：可读项目代码、检索网络、查询本工作区已有意图，也可向你提问澄清，但不能改文件或执行命令。它把想法整理成覆盖五维的条目，并标注优先级、影响范围、模块和依赖。
5. **在对话里确认后才落库。** 智能体须先在对话中列出本轮全部意图并取得你的明确文字确认，再调用保存。调用即写入，不弹权限窗；校验失败整批零写入。新保存的条目以 `todo` 起步。没有你的确认，任何意图都不会经这条路径落库。

### 创建意图·方式二：从多智能体讨论转化

方向还不明朗时，先发起一场[讨论](discussion.md)。讨论完成且结论非空时，点击转化为意图（Convert to Intent），结论送入同一个创建原语，同样经过沟通与确认后落库。

### 创建之后：从意图到开发

意图入库后，后续的典型路径是：

```
意图（todo）
   → [有效模式要求规格时] 撰写规范 → 只读审核 → 批准（人工，或工作区显式允许的机器批准）
   → Start Work 启动开发（已有会话则挂接或续跑，否则新建；默认可选 worktree 隔离）
   → 提交 / 推送 / 建 PR（可关联交付）→ 评审 / 修复 → 标记 done
```

- **细化：** 已保存的意图可开沟通会话继续打磨；有 id 则原地更新，不产生重复。标题或正文实际变化时撤销规格批准。
- **规格：** 工作区 SDD 总开关默认开启，每条意图可用 `specMode` 覆盖。详见 [SDD](sdd.md)。
- **依赖：** 未满足时列表警示；真正放行看前序产出是否已在基线上。队列不提供一次性放行。
- **队列：** 勾选 `automate` 并启动该工作区的意图队列后，c3 按优先级与最早创建挑选，规格阶段可自治撰写 / 审核 / 有限返工，开发失败则退避、连续三次挂起。权限等待超时只挂起并待办，不代答。这与[自动化](automation-engineering.md)页上的 cron / 事件任务不是同一套调度。
- **交付：** 意图 PR 可打向交付分支，一批意图共同验证后再进入主线。见 [交付](delivery.md)。

> 小提示：第一次尝试时，选一个小而清晰的想法（比如"给某个模块补一个校验"），完整走一遍"新建 → 确认 → 启动开发"的流程，感受意图与直接在会话里输入 prompt 的差别。

### 常见问题

**Q：意图和直接在会话里输入 prompt 有什么区别？**

A：会话 prompt 是一次性的——对话结束，上下文就散了。意图是持久的结构化记录，可以细化、依赖、排期、进队列，并关联完整的开发与交付链路。小事直接聊，正经的功能演进用意图。

**Q：意图沟通智能体会不会偷偷改我的代码？**

A：不会。它的只读约束在工具层强制执行（不是靠提示词自觉）：编辑、写文件、执行命令、派生子智能体与斜杠命令被硬性禁用。

**Q：意图会不会未经我同意就被保存？**

A：沟通路径不会。保存必须先有你在对话中的明确确认；调用即落库，不走权限 Allow/Deny。外部 MCP 或机器人若被管理员勾选了写工具，则以那次授权替代对话确认，业务校验不放宽。

**Q：一个大想法应该建一个意图还是多个？**

A：交给沟通智能体拆——它会拆成多个大小合适、依赖关系明确的意图，同一批保存的条目之间也可以声明先后依赖。原则是：一个可独立完成、可独立验证的目标为一个意图；同一目标的代码、测试、文档永远在同一个意图里。
